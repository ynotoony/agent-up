# 已治理仓升级手册

目标项目已按本体系初始化（初始那套文件都在）后，公开包演进出新版（新脚本、新模板、新条款），升级＝**把你仓里已经装上的部分，经你确认后对齐到包的新版本**。升级不是重装：既有事实、记录与用户改过的一切照旧，动的只有你确认要跟的件。

## 1. 判别与盘点（动手前完成）

- 判别：仓里已有初始化装上的那套文件（`AGENTS.md`＋`rules/` 规则三件＋`facts/project/artifacts.yaml`，含旧布局形态）就是升级候选；以用户话语（"升级/同步包新版/拉新模板"）确认进入本手册，不单凭文件存在性自行定轨。
- 盘点已装的部分（列成清单供第 2 步对比）：
  - **装上的脚本**：`rules/implementation/scripts/`（新布局）或 `scripts/`（旧布局）内来自包的件（artifacts.yaml 里登记了 `generated_from` 指向包内路径的条目）。
  - **模板生成的文件**：`rules/assessment.md`、`rules/implementation/discipline.md`、`rules/project.md`、各 README、`AGENTS.md`（登记 `generated_from` 指向包内 `.tmpl`）。
  - **配置**：仓根 `delivery.rules`（如有）。
  - 包的新版本：用户 clone/pull 后的包目录（本手册命令里的 `<pkg-dir>`）。

## 2. 逐件对比（三种情况）

跑 `sh <pkg-dir>/scripts/upgrade-check.sh <pkg-dir> <repo-root>`（全程只读），或人工逐件 `cmp`。每个文件只有三种情况：

| 态 | 判定 | 含义 |
| --- | --- | --- |
| 一致（工具输出作"同步"） | 和包内版本相同（字节一致或关键节都在） | 无需动作 |
| 落后 | 包里有新版（或新件），仓内是旧版/缺失，且没有人工改过的迹象 | 可以跟新版，走第 3 步确认 |
| 改过（漂移） | 仓内文件和包的任何已知版本都不一样（人工改过或本地演化） | **停**：报告用户，等裁决（保留你的改 / 放弃本地改跟包 / 登记分歧保持现状）。**源仓例外**：若本仓即包的源仓/维护者（仓内携带包目录与导出配置），"仓领先于包"（仓侧演进而包内未同步）时三选项均不适用——唯一合法出口＝先修包（开票把包内落后件翻值，内容可取自仓侧现值，落点必须先是包）→ 按交付流程推送并同步本机技能 → 再以消费者身份用本机技能包基线复跑本对账器至全同步；顺序不可倒置，禁止绕开修包直接手工搬文件"修仓"。 |

模板生成的文件（rules/ 三件等）项目侧可能合法改写过（项目自有条款槽位本就设计为随生长追加），对账器只标"落后"不判"改过"——是否采纳新版条款由你按第 3 步逐件决定，执行体不得整文件覆盖。对账器对规则三件做**规则块集核对**（抽取 `#### R-XX-NNN` 标题 ID 集合与包内模板比对）：实例缺块＝落后（逐块列 ID，吸收或登记分歧归第 3 步裁决）；实例有模板没有的块＝**登记分歧候选**（只提示不拦截——登记过的实例口径如按项目裁剪启用面，正落在此列）；块内语义差异归独立 Review，对账器不判。

## 3. 差异清单确认（确认前零写入）

按 `SKILL.md` 主流程步骤 4 通用规则执行（含现状与目标、四类分组、执行形态与预估）；升级态额外要求：

- **将更新**一列逐件标注来源版本去向（旧拷贝 → 包新版），让你看清每一件跟不跟。
- 改过的文件逐件给三选项（保留你的改／跟包／登记分歧），你逐项裁决后才能进第 4 步。
- 新增件（包有而仓无，如新模板、新脚本）单列，标注其触发条件与生成义务（如 `delivery-rules.tmpl` 生成 `delivery.rules` 归仓根）。

## 4. 对齐更新（确认后逐件）

- 规则权威＝目标项目 `rules/project.md` 的对齐更新节（发现被改过即停、写入前备份、重复执行结果一致），本手册不复制判据，只定顺序：
  1. 先更新脚本（`install.sh --target <repo-root> <门控>`：已一致的自动跳过、复制新增件、发现被改过即停）。**源仓语境**：源仓/含包副本的仓安装目的地（`rules/implementation/scripts/`）与复制基线（`agent-up/scripts/`）是不同目录，安装器的包内误运行守卫只拦"目标即包根本体／目标＝脚本所在目录／落位目录＝脚本所在目录"三类自写自毁场景，源仓经 `install.sh` 正常安装，无须绕开脚本手工搬文件；
  2. 再配置面（`delivery.rules` 按模板生成或按 diff 逐节对齐——锚点行逐字匹配，禁手抄）；
  3. 后更新模板生成的文件（逐件：备份现件 → 按新模板重生成 → 项目自有条款与【按项目填写】值按现件回填 → 你确认关键条款 diff）；
  4. 每件更新后重跑该件配套验证（脚本 `sh -n`＋家族夹具；条款件过包对账器）。
- 解析器族升级（内嵌 `dp_load_rules` 的四脚本）按 `old-project.md` §3 dp_load_rules 引擎件行同步六 hunk，或整件对齐包新基线后核 `# dp-parser` 注记一致。
- 记录类产物（决策账本、状态索引、运行记录）与用户事实**不在升级范围**：模板升级不得覆盖（R-DP-003 口径），永不触碰。

## 5. 验证与收尾

- 全套验证：包自检 `sh <pkg-dir>/scripts/check-package.sh`；仓侧检查（装好的 check-artifacts/check-stale-claims/check-gates 一族）；`upgrade-check.sh` 复跑确认差距清零或只剩你决定保留的项。
- **Derived 面回访**（升级专属步骤，R-DP-040 检查面）：对账派生文件——项目地图触发矩阵命中而未生成＝欠账，补生成；已生成但代码拓扑已变未再生＝标 `stale`（R-DP-009 口径，恢复前不当可信导航）。三态为本步骤自定义（比对轴是拓扑新鲜度，非 §2 的包版本轴）：未生成且命中＝欠账（补）、已生成且拓扑未变＝同步、已生成但拓扑已变未再生＝落后（再生）；漂移判定不适用（Derived 可再生，不存在"人工改过"保护面）。
- **历史票清洗扫描**（升级专属步骤，R-DP-039 清洗面）：升级时对存量票面做一次清洗扫描，专找"看着像现行规定、实际已与权威层对不上"的危险内容——票面说明与 rules 三件/specs 冲突、`superseded` 票的说明仍被现行票引用、与新版模板条款相抵的旧口径句。输出危险票名单（票 id＋冲突点＋建议处置），**交用户逐票裁决**：名单本身零改写，裁决后走收口搬运（说明提炼进规则/事实层，R-DP-039 第 4 面）或替代标记（索引登记 `superseded_by`）。不升级时不主动扫描（翻到谁处理谁）。
- 收尾报告按 `SKILL.md` 步骤 9，额外列：更新件清单（旧→新）、改过件的裁决结果、登记同步情况（artifacts.yaml 条目 `generated_from`/update_policy 括注随更新件刷新）、清洗扫描结果（名单与你的裁决，未执行写 `N/A + reason`）。
- **对账报告标准四节**（升级对账的固定呈现格式，upgrade-check 输出即骨架，收尾报告照此四节组织、不再自由发挥）：①同步面——逐件列（脚本/配置/规则块集一致件）；②差异面——落后/漂移/分歧候选三分列，每项带证据（文件与块 ID）；③Derived 面——欠账/过期/再生记录；④结论行——全同步或差距 N 项待裁决（逐项挂处置：吸收/登记分歧/再生）。

## 6. 包基线获取

包的新版本＝公开仓最新 main（`git clone`/`git pull` 更新包目录）；更新了什么读包根 `CHANGELOG.md`（每次发布一条）。没 pull 的旧包目录不能当升级基准——先更新包，再谈升级仓。
